## 2. 实施基线与范围

### 2.1 当前实现

| 位置 | 已有能力 | 本阶段切入点 |
| --- | --- | --- |
| `agents/main.py::build_agent` | 构造模型、系统提示词、`tools=[]`、Checkpointer | 增加 `middleware` 与 `context_schema` |

### 2.3 阶段边界

生产 Agent 仍使用 `tools=[]`。测试中的 `echo` 工具只验证框架行为，不进入生产工具列表或 CLI。五种基础工具、多模态、工具错误转换、工具轨迹事件、Permission、Todo 和 SubAgent 按总方案留在后续阶段。

不新建 HookRegistry、插件发现机制、通用 middleware 配置语言、第二套预算计数器或执行循环。生产端本阶段只需要官方预算 middleware；不为展示 hooks 添加无实际用途的日志、空壳或探针 middleware。

会话记录继续使用 callback。不添加 hook 轨迹事件，不从 trajectory 恢复状态，不迁移旧会话。验收使用新建临时 session。

## 3. 关键设计决策

### 3.1 组合入口

新增 `agents/middleware.py::build_middleware(config)`，返回按执行顺序排列的官方 `AgentMiddleware` 实例列表。每次构建 Agent 时创建新实例，避免在模块级保存共享实例或可变运行状态。

计划中的最小实现为：

```python
from langchain.agents.middleware import AgentMiddleware, ModelCallLimitMiddleware

from ..config import Config


def build_middleware(config: Config) -> list[AgentMiddleware]:
    return [
        ModelCallLimitMiddleware(
            run_limit=config.runtime.max_model_calls,
            exit_behavior="error",
        ),
    ]
```

`build_agent` 将该列表直接传给 `create_agent(middleware=...)`。后续阶段需要新行为时，在此入口显式增加实例并验证组合顺序。本阶段不增加运行时注册、覆盖生产列表或关闭预算的 CLI 参数。

### 3.2 调用预算

在现有 `[runtime]` 中增加：

```toml
[runtime]
# 保留现有路径字段；一次用户交互最多允许的模型循环调用次数。
max_model_calls = 10
```

| 项目 | 本阶段约定 |
| --- | --- |
| 配置字段 | `RuntimeConfig.max_model_calls`，默认 `10` |
| 校验 | 严格正整数；拒绝 `0`、负数、布尔值、浮点数和字符串；可使用 `Field(default=10, gt=0, strict=True)` |
| 生效范围 | 当前一次 `agent.ainvoke`，对应目前的一次 `ask` 交互 |
| 官方参数 | `run_limit=max_model_calls`；不设置 `thread_limit` |
| 超限策略 | 固定 `exit_behavior="error"` |
| 配置展示 | `Config.summary()` 增加该字段；无需增加 CLI 参数 |

默认值 `10` 是本阶段的产品选择，不是 LangChain 的默认值。缺少该字段的配置使用默认值；现有本地 `config/default.toml` 无需覆盖。

预算行为以当前官方实现为准：

1. 正常完成第 N 次模型调用并返回最终回答时，`run_limit=N` 允许成功；只有尝试第 N+1 次调用才报错。
2. 超限抛出 `ModelCallLimitExceededError`。应用沿用现有异常捕获，返回 `status="failed"`、`answer=null` 和 `error.type="ModelCallLimitExceededError"`，记录 `interaction_failed`。不改成成功回答，也不自动重试。
3. 新一轮 `ainvoke` 获得新的 run 预算。同一 session 的累计调用次数不限制后续对话；错误后的新请求也按新一轮处理，不隐式恢复上一轮失败执行。
4. 官方计数随框架 State 管理。当前版本在 `after_model` 增加计数，run 计数字段使用 `UntrackedValue`；应用不手动清零、不向 session 元数据写入预算状态，也不自行复制官方 State 字段。
5. 预算约束模型循环中的调用，不能等同于 provider 的 HTTP 请求、SDK 内部重试、token 或费用硬上限。模型异常保持原有错误路径。
6. 第 N 次模型响应若包含工具调用，工具仍可能执行；middleware 会在随后尝试第 N+1 次模型调用时拦截。预算不撤销已执行的动作，也不代替后续 Permission 或工具调用次数限制。

采用 `error` 是因为当前应用将正常返回的最终消息视为成功；使用 `end` 会引入人工生成的终止回答，还需要额外识别结果状态。当前方案可以直接复用已有失败接口。[官方调用限制说明](https://docs.langchain.com/oss/python/langchain/middleware/built-in#model-call-limit)

预算拦截发生在模型节点之前，被拦截的第 N+1 次调用不应出现 `model_start`。错误来自 middleware，也不要求出现 `model_error`；可观察的终点是 `interaction_failed`。

### 3.3 Runtime context 注入

在 `agents/main.py` 就近定义：

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class AgentContext:
    workdir: str
```

仅加入已确定需要的 `workdir`。`session_id` 已通过 `configurable.thread_id` 传递，`interaction_id` 已在 callback metadata 中，不重复放入 context；API key、整份配置、消息历史和预算计数也不放入 context。

接线方式：

```python
# agents/main.py：保留现有模型、提示词、tools=[] 与 checkpointer 参数。
create_agent(
    ...,
    middleware=build_middleware(config),
    context_schema=AgentContext,
)

# application.py：取得会话交互锁、重读 session 元数据之后。
await agent.ainvoke(
    {"messages": [message]},
    config=existing_run_config,
    context=AgentContext(workdir=session.meta.workdir),
)
```

以上为接线示意；`existing_run_config` 表示现有调用配置，不要求新增变量或封装层。

node hooks 通过 `runtime.context` 读取，wrap hooks 通过 `request.runtime.context` 读取；未来工具通过 `ToolRuntime[AgentContext]` 读取。context 来自 session 中已经解析的工作目录，不从本轮用户文本或模型可见工具参数获取。[官方 context schema 说明](https://docs.langchain.com/oss/python/langchain/agents#context-schema)

context 是每次调用注入的运行依赖，不是新的 Agent State 字段；重启后重新从 session 元数据构造。保持既有系统提示词中的工作目录说明，不因接入 context 改变提示词。测试应检查 context 对象没有被自动写入 Checkpoint state 或工具 schema，不能据此要求工作目录字符串在所有消息中消失。

### 3.4 Hooks 与状态更新

生产入口使用 `ainvoke`，自定义扩展及验收探针均优先实现异步接口：

| 扩展点 | 异步接口 | 本阶段测试内容 |
| --- | --- | --- |
| Agent 开始、结束 | `abefore_agent` / `aafter_agent` | 成功调用中各执行一次，覆盖完整模型—工具循环 |
| 每次模型调用前后 | `abefore_model` / `aafter_model` | 多次模型调用均执行；返回 State 增量 |
| 模型调用包装 | `awrap_model_call` | 嵌套顺序、读取 context、`await handler(request)`；用 `request.override(...)` 验证临时请求调整 |
| 工具调用包装 | `awrap_tool_call` | 嵌套顺序、读取 context、正确返回工具结果与 `tool_call_id` |

官方预算 middleware 已提供异步 hooks。RSH 暂不承诺同步 `invoke` 入口，不为本阶段测试复制一套同步扩展。[官方自定义 middleware 文档](https://docs.langchain.com/oss/python/langchain/middleware/custom)

用两个名称不同的测试 middleware A、B 验证以下顺序；探针仅在测试文件中定义：

```text
abefore_agent: A → B
每次模型调用:
  abefore_model: A → B
  awrap_model_call: A进入 → B进入 → model → B退出 → A退出
  aafter_model: B → A
需要工具时:
  awrap_tool_call: A进入 → B进入 → tool → B退出 → A退出
  然后进入下一次模型调用
aafter_agent: B → A
```

同一模型响应中有多个独立工具调用时，只断言每个调用内部的包装顺序和结果配对，不断言工具之间的完成顺序，不添加 `parallel_tool_calls=False`、`max_concurrency=1` 或批次拒绝逻辑。

测试 State 继承 `AgentState`，仅定义 `probe_count` 等测试字段，并由 middleware 的 `state_schema` 声明。node hooks 返回增量字典；测试其对后续节点可见、能够保存和恢复，且不破坏 `messages` 的既有 reducer。模型请求的临时修改通过 `request.override(...)` 完成，不通过原地修改 `state["messages"]` 实现。

探针的事件列表用于断言，不能作为生产状态存储模式。生产可变执行状态交给框架 State；middleware 实例只持有配置。`aafter_agent` 是正常完成时的 hook，不是异常或取消时必定执行的 `finally`；已有 session 锁和 Checkpointer 上下文管理继续负责资源释放。
