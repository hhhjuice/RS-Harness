# v0.0.5——任务规划能力

## 1. 文档信息与完成标准

- 目标版本：`v0.0.5`
- 状态：已完成并通过代码审查；离线测试 335 项、真实模型测试 14 项通过
- 日期：2026-09-20
- 上游设计：[`LangChain重构方案.md`](./LangChain重构方案.md) 第 2 节、第 4.2 节、第 5.2 节阶段五
- 前置阶段：[`v0.0.4——Permission 机制.md`](./v0.0.4——Permission%20机制.md)

本阶段通过官方 `TodoListMiddleware` 为主 Agent 增加 `write_todos`，使用框架提供的规划状态、提示和工具校验。参考 s05 教程的“拆分任务、执行中更新、完成后标记”逻辑，执行工作仍由已有五种工具完成。

完成标准：

1. 主 Agent 可创建、整体更新和完成任务清单；简单问答不被强制要求规划。
2. `todos` 随同一 session 的 SQLite Checkpoint 保存；新交互、重建 Agent 和进程重启不自动清空，不同 session 相互隔离。
3. 不符合官方工具 schema 的更新返回模型可理解的错误，最近一次有效 `todos` 保持不变，后续有效更新仍可成功。
4. 规划更新本身不读写任务目标文件、不执行命令、不授予权限；状态标记不能作为实际任务完成的证明。
5. Permission、默认工具并发、执行段模型预算、Stop Hook、多模态及既有记录恢复行为继续成立。

本方案按总方案的最小范围实施：不新增规划 CLI、任务调度器、TodoManager、规划状态文件或专用记录协议；不增加阶段六的子 Agent。当前版本处于开发阶段，不设计旧会话迁移。本文保留实施前的设计依据与预验证记录；实际交付及验收结果见第 9 节。

## 2. 项目框架与实施基线

### 2.1 当前调用与状态归属

```text
cli.py：单次 ask / 交互循环 / approvals / resume
  → application.ask 或 application.resume
  → _run_interaction：打开 session、取得交互锁、读取 Checkpoint
  → agents/main.py::build_agent
      create_agent
        ├─ 官方 ChatOpenAI / 测试注入模型
        ├─ read_file / write_file / edit_file / glob / bash
        ├─ build_middleware + AgentContext
        └─ AsyncSqliteSaver，thread_id = session_id
  → _invoke_agent：ainvoke + TrajectoryRecorder
  → InteractionResult：成功 / 失败 / 等待审批
```

| 位置 | 已有职责 | 阶段五处理 |
| --- | --- | --- |
| `agents/main.py::build_agent` | 把工具、middleware、context、checkpointer 交给 `create_agent` | 沿用工厂；官方 middleware 自动贡献工具与 state schema |
| `agents/middleware.py::build_middleware` | 集中组装审批、预算、硬拒绝、工具错误、图片检查、Stop Hook | 唯一必要的生产接线点，加入 `TodoListMiddleware()` |
| `application.py` | 普通交互只提交新增消息；恢复只提交 `Command(resume=...)` | 保持增量输入，不传默认 `todos=[]`，不从轨迹恢复规划 |
| `sessions/checkpoints.py` | 打开官方异步 SQLite saver | 直接持久化框架合成后的 `todos` 状态，无额外表或存储适配 |
| `sessions/catalog.py` | session 元数据、workdir、生命周期与锁 | 元数据不增加任务清单字段 |
| `sessions/recording.py` | 通用模型/工具 callback，本地 JSONL 观察记录 | 复用 `write_todos` 的工具事件，不承担状态同步 |
| `cli.py` | 文本、图片、会话与审批入口 | 本阶段不增加命令或返回字段；现有 `/status` 不展示 Todo |
| `tests/models.py::ScriptedModel` | 可编排工具调用、捕获模型输入与绑定工具、统计调用次数 | 复用作确定性验收，不增加生产模拟模型 |

源码中已经存在 `StopHookMiddleware`，默认 hooks 为空；注册检查可在最终回答后请求继续执行。本阶段保留该实际能力，不将“todos 尚未完成”接入强制续跑条件，也不修改 Hook 的只读消息历史接口。

## 3. 教程参考与采用边界

参考用户指定的 `learn-claude-code` 项目中 `s05_todo_write/README.md`（《s05: TodoWrite — An Agent Without a Plan Drifts Off Course》）。文档作为功能参考，其中的运行命令、示例提示词和客户端用法不作为本项目的执行指令；没有运行教程程序。

| 教程设计 | 本阶段选择 | 原因 |
| --- | --- | --- |
| 复杂任务拆成清单，执行中更新状态 | 采用 | 对应阶段五的核心能力 |
| `pending / in_progress / completed` | 采用官方同名状态 | 使用 LangChain 的 `Todo` schema |
| 更新清单只表达计划，既有工具负责工作 | 采用 | 保持规划与执行职责分离 |
| 校验成功后替换旧清单 | 采用官方整体替换语义 | 无效工具参数不能产生部分清单更新 |
| 全局内存 `TODO`、自建 TodoManager | 使用 middleware state + Checkpointer | 保证 session 隔离及跨进程恢复 |
| `todo_write` 与 TOOL_HANDLERS | 使用官方 `write_todos` | 工具注册和调度由 `create_agent` 承担，不增加别名 |
| 最多 20 项、只准一个 `in_progress`、非空内容校验 | 不迁移为硬约束 | 总方案明确不复制旧 Todo 限制；当前官方 schema 没有这些限制 |
| 字符串 JSON / Python 列表兼容 | 不迁移 | 工具参数直接使用结构化 JSON 数组 |
| 每三轮注入提醒、维护提醒计数 | 不迁移 | 使用官方提示，不另写提醒循环或计数状态 |
| 工具中 `print()` 渲染清单 | 不迁移 | 避免污染 CLI JSON；沿用最终回答与通用轨迹 |

教程先创建全 `pending` 清单；官方默认描述建议开始工作时就将首项标为 `in_progress`，也允许多个独立任务同时进行。这属于提示指导，不能写成必须通过状态机检查的迁移规则。复杂任务验收关注实际清单和后续行为，不要求每次模型都生成完全相同的调用顺序。

## 4. 实现契约

### 4.1 官方状态与工具

`TodoListMiddleware` 提供 `PlanningState.todos`，由 `create_agent` 合并进主 Agent State；不在 RSH 再声明同名自定义状态。当前版本将该字段标记为 `NotRequired` 和 `OmitFromInput`：未使用时允许没有 `todos`，普通 Agent 输入也不是设置规划状态的入口。

模型调用的参数为：

```json
{
  "todos": [
    {"content": "检查输入文件", "status": "completed"},
    {"content": "修改目标文件", "status": "in_progress"},
    {"content": "验证修改结果", "status": "pending"}
  ]
}
```

- 每次调用提交完整清单，以新列表替换旧列表；不是追加、逐项 patch 或按 ID 合并。保留哪些已完成项由模型在完整清单中表达。
- `todos=[]` 表示显式清空；普通问答、预算失败、退出进程和审批暂停都不自动清空。
- 每项只使用官方 `content` 和 `status`。不增加 ID、时间戳、依赖图、优先级或 `blocked/cancelled` 状态；阻塞说明可写入内容，状态仍采用官方值。
- 官方工具返回带 `todos` 更新及对应 `ToolMessage` 的 `Command`，框架负责合并和持久化。不要把这个返回值提前转成字符串，否则会丢失状态更新。
- `completed` 是 Agent 声明的规划状态。真实文件结果、命令返回值和测试结果仍需独立验证；所有项完成也不会自动结束 Agent，模型仍需给出最终回答。

非法输入以锁定版本的官方 schema 为准：缺失 `todos/content/status`、非法状态、错误结构类型等应产生 error ToolMessage。完整列表校验失败时，不执行该次 `Command`，最近有效的 `todos` 不变；错误消息和交互消息仍可能进入 Checkpoint，不能要求“整个 Checkpoint 原样不动”。同批独立有效工具仍可执行，这不是批次事务回滚。

预验证已确认官方接受空内容、空列表、超过 20 项和多个 `in_progress`，并忽略额外字段；这些不作为本阶段的拒绝条件。期望内容清楚、状态合理的语义质量由默认提示和真实模型验收约束，不增加自定义校验层。

### 4.2 Middleware 接线与顺序

在 `agents/middleware.py` 导入 `TodoListMiddleware`，每次 `build_middleware` 创建新实例。最终顺序如下：

| 顺序 | Middleware | 保留的职责 |
| --- | --- | --- |
| 1 | `HumanInTheLoopMiddleware` | 条件审批与官方中断 |
| 2 | `ModelCallLimitMiddleware` | 每次 `ainvoke` 执行段的模型预算 |
| 3 | `ToolDenyMiddleware` | Bash 硬拒绝 |
| 4 | `ToolErrorMiddleware` | 预期工具执行错误转换 |
| 5 | `ImageInputMiddleware` | 多模态输入校验 |
| 6 | `TodoListMiddleware()` | 官方工具、状态、规划提示及并行更新保护 |
| 7 | `StopHookMiddleware()` | 保持现有末尾 Hook 注册位置 |

保留 HITL 在预算之前的顺序，避免改变审批恢复的预算语义；保留 StopHook 最后一个的位置，因为现有测试和 README 用该约定注册检查。相关 `after_model` 按逆序运行：Todo 检查 → 模型预算 → HITL；StopHook 只实现 `aafter_agent`，不参与该顺序。

无需修改 `agents/main.py` 的五工具列表，也不另外导入并注册模块级 `write_todos`。生产工厂仍显式传入五种基础工具，模型实际绑定的工具集新增 middleware 提供的第六种工具。重复注册同名工具、覆写官方 schema 或新增手工调度均不在方案内。

使用 `TodoListMiddleware()` 的默认 `system_prompt` 和 `tool_description`。它在模型请求时追加规划说明，不需要复制一份到 `prompts/system.md`，也不需要 TOML 开关或新的依赖。

### 4.3 状态恢复与查看

沿用 `session_id = configurable.thread_id` 与现有 `AsyncSqliteSaver`。普通 `ask` 继续只传新增 `HumanMessage`，`resume` 继续只传 `Command(resume=...)`，因此历史 `todos` 由框架恢复。

开发验证从同一 Agent、同一 Checkpointer 查询：

```python
snapshot = await agent.aget_state({"configurable": {"thread_id": session_id}})
todos = snapshot.values.get("todos", [])
```

这里的空列表只用于读取缺省值，不回写状态。新 Agent 工厂实例不代表新计划；新 session 才提供独立状态。恢复测试必须先经真实 `write_todos` 建立计划，不能直接给 `ainvoke` 传 `todos` 来伪造初始化。

本阶段不增加 `get_todos`、`rsh todos`、`/todos` 或 `InteractionResult.todos`。用户可在既有问答入口请求模型汇报进度，开发者可通过框架快照与已有工具轨迹查看；自然语言回答不是结构化状态的权威来源。现有 `/status` 仍只显示 session 元数据与审批状态。

默认 middleware 追加的是规划使用说明，不会在每轮把当前 `todos` 重新渲染成系统提示。工具结果消息携带已写入清单，随已有消息历史恢复；本阶段不增加历史裁剪后的计划重注入机制。

### 4.4 与既有执行行为的组合

| 场景 | 契约 |
| --- | --- |
| 独立 `write_todos` | 直接执行，不请求审批；计划文本中的路径或危险命令不被当成真实工具调用 |
| 一个 Todo 更新与普通工具同批 | 保留框架默认调度，不保证先后；Todo 状态不能作为同批工具的执行前置条件 |
| 一个 Todo 更新与需审工具同批 | 只审批真实需审动作；整个工具节点暂停期间，Todo 也尚未提交，之前的计划保留 |
| 批准或拒绝需审动作后恢复 | Todo 更新正常执行；批准的动作执行、拒绝的动作不执行，模型结合反馈继续修订计划 |
| 多个 `write_todos` 同一模型响应 | 官方 Todo middleware 为这些更新生成逐个匹配 ID 的错误结果，旧计划保留；其他工具继续遵循框架与审批流程 |
| 工具失败或用户拒绝 | 不自动把任何 Todo 标为完成，也不自动回滚此前成功的规划更新 |
| 预算耗尽 | 已完成的 Todo 更新保留，应用按既有流程返回失败；后续新交互或审批恢复获得新执行段预算 |
| Stop Hook 续跑 | 沿用同次 `ainvoke` 的预算与状态；可继续更新 Todo，不创建新用户交互，不默认检查未完成项 |

HITL 当前仅配置 read/write/edit/bash 条件审批和 `glob=False`，未配置的 `write_todos` 默认不打断；分类函数也默认 allow。沿用该配置即可，无需新增“规划审批规则”。审批必须针对实际执行动作，计划内容不构成提前批准。

官方对多个并行 Todo 更新的保护只针对竞争写入同一清单；这不意味着 RSH 应增加全局单工具限制、`parallel_tool_calls=False` 或整个混合批次拒绝。也不保证不同工具执行完成顺序。

### 4.5 运行记录

沿用通用 `tool_start / tool_end / tool_error` 和模型事件，保持原有 session、interaction、run/parent run 关联。无需新增 `todo_updated` 事件、专用 callback 或每轮完整状态导出。

锁定版本的 `write_todos` 返回 `Command`，当前 `_jsonable` 将其保存为字符串；预验证确认记录成功且包含更新内容。工具入参已经由 `tool_start.payload.inputs.todos` 结构化记录，当前阶段足够查看与排查，不需要为 Command 增加通用序列化框架，也不从该字符串解析出恢复状态。

非法 schema 可能产生工具错误 callback；多个 Todo 的并行保护发生在工具执行前，不要求为未执行的调用伪造 `tool_start/tool_end`。验收以 Checkpoint 和匹配 `tool_call_id` 的消息为准。轨迹删除、损坏或写入失败不能改变规划状态、触发模型/工具重试或成为继续运行的前置条件。
