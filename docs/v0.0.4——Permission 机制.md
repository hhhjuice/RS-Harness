## 2. 项目理解与实施基线

### 2.1 当前执行与存储边界

```text
cli.py
  ├─ ask_command：构造本次文本/图片消息
  └─ _interactive：在同一事件循环内处理多轮输入
       ↓
application.ask
  SessionCatalog.open → Session.interaction_lock
  → open_checkpointer → build_agent → agent.ainvoke
  → extract_answer → InteractionResult + trajectory
       ↓
agents/main.py
  create_agent + 五工具 + build_middleware + AgentContext
```

- **框架状态**：`sessions/checkpoints.py` 打开官方 `AsyncSqliteSaver`；`session_id` 直接作为 `configurable.thread_id`。消息由框架维护，每轮仅提交一条新 `HumanMessage`。
- **会话生命周期**：`sessions/catalog.py` 保存 workdir、模型标识、时间和 `running/closed`。`interaction_lock()` 使用非阻塞文件锁，取得锁后重读元数据；关闭也经过同一把锁。
- **运行依赖**：`AgentContext` 每次注入 session workdir、Bash 超时和输出预算；不作为持久消息或模型可传参数。
- **运行记录**：`TrajectoryWriter` 和官方 callback 保存本次交互及模型/工具事件。每次调用的 metadata 已包含 `interaction_id`，现有 Checkpointer 测试已验证它进入 Checkpoint metadata。
- **现有工具边界**：文件工具解析路径并一律拒绝 workdir 外访问；Bash 使用该目录作为 cwd，但没有 OS 沙箱。修订后文件越界改为条件审批，因此必须同步调整文件工具，不能批准之后仍被旧边界无条件拒绝。

### 2.2 本阶段实际缺口

| 位置 | 现状 | 本阶段需要补齐 |
| --- | --- | --- |

## 3. 参考逻辑与危险操作策略

### 3.1 参考范围与三种结果

参考文件：用户提供的 [s03 README](/Users/hgz/WorkSpace/NoteBooks/MyNotes/Agent/learn-claude-code/s03_permission/README.md) 和 [s03 code.py](/Users/hgz/WorkSpace/NoteBooks/MyNotes/Agent/learn-claude-code/s03_permission/code.py)。这里只采用它们的审批规则及优先级；示例中的 Anthropic 客户端、环境变量加载、`input()`、自建 agent_loop 和 TOOL_HANDLERS 不作为新版实现方式。

对每个调用按 **deny → ask → allow** 判定，不按工具名称一律要求审批。首版规则与参考示例保持一致：

| 工具 / 操作 | 判定 | 行为 |
| --- | --- | --- |
| Bash 命中 `rm -rf /`、`sudo`、`shutdown`、`reboot`、`mkfs`、`dd if=`、`> /dev/sda` 任一子串 | deny | 直接返回带原因的错误 ToolMessage，不执行、不进入人工审批 |
| Bash 未命中 deny，但命中 `rm `、`> /etc/`、`chmod 777` 任一子串 | ask | 暂停，用户可 approve/reject |
| `read_file` / `write_file` / `edit_file` 的解析目标位于 session workdir 外 | ask | 暂停；批准后允许当前这次外部文件访问，拒绝则不执行 |
| 上述文件工具目标位于 workdir 内 | allow | 直接执行，包括普通创建、覆盖和精确编辑 |
| Bash 未命中以上规则，例如 `pwd`、`ls`、`cat note.txt`、`pytest` | allow | 直接执行 |
| `glob` | allow | 保持工作区内查询；绝对模式、`..` 等非法模式仍由工具报错，不增加越界 glob 能力 |

deny 的优先级高于 ask，例如 `sudo rm file.txt` 直接拒绝，不能把硬拒绝降级成一次可批准操作。读取工作区外文件同样需要审批，参考代码的文件规则包含 read_file，不能被其“Writing outside workspace”提示文案误导。

这里的危险操作以明确的规则集定义。Bash 按参考代码对原始命令字符串做区分大小写的子串匹配；例如 `rm -rf /tmp/demo` 也会命中 `rm -rf /` 而硬拒绝，引号或注释中的关键词可能误报，变量、不同空白写法和脚本间接执行也可能漏报。这是可复现的小型策略，不是 Bash 语义分析或 OS 沙箱，不声称识别所有危险命令。本阶段不扩建 Shell 解析器、通用规则语言或安全隔离系统。

### 3.2 LangChain 标准接线

在 `agents/middleware.py` 就近定义一个无执行副作用的判定函数，例如 `classify_tool_call(tool_call, workdir) -> (decision, reason)`，供以下两个官方扩展点共用。函数只描述规则，不维护许可记录、用户交互或工具调度。

1. **需要询问**：`HumanInTheLoopMiddleware.interrupt_on` 对 read_file/write_file/edit_file/bash 配置 `when=needs_approval`，只在判定为 ask 时返回 True；`allowed_decisions` 固定为 approve/reject。glob 配置为 False。`needs_approval(request)` 读取 `request.tool_call` 和 `request.runtime.context.workdir`；当前版本构造的 `request.tool` 为 None，不能依赖工具实例。
2. **硬拒绝**：一个小型 `ToolDenyMiddleware(AgentMiddleware)` 实现 `awrap_tool_call`。命中 deny 时返回 `ToolMessage(status="error", tool_call_id=原ID, name=工具名, content=拒绝原因)`，不调用 handler；否则 `await handler(request)`。不抛出终止整轮的业务异常，也不手工执行其他工具。
3. **直接执行**：when=False 不创建人工中断，非 deny 调用由原有官方工具节点执行。deny 的 when 也为 False，其执行拦截由必选的 ToolDenyMiddleware 完成；生产接线测试必须同时覆盖这两个组件。

`when` 和硬拒绝 hook 共用同一套规则，不能各写一份清单。审批 description 显示命中的规则、原参数及文件的解析目标；动态 description 使用当前版本的 `(tool_call, state, runtime)` 签名，when 则使用 `ToolCallRequest` 签名。类型错误、缺少参数等不在谓词中执行工具或随意抛出 KeyError/TypeError，仍交由已有 schema/工具错误路径处理。

批准只允许当前调用以原参数执行；拒绝由官方 HITL 形成 error ToolMessage。批准不保证 OS 权限、文件类型、唯一匹配、Bash 超时等执行条件满足。模型若提出另一项危险操作，需再次审批；不保存永久授权，不提供批准全部的运行开关，也不接受模型传来的 approved/allow_outside 参数。

### 3.3 文件访问边界的必要调整

为使“越界访问 → 审批 → 执行”成立，工作区边界从文件工具中的无条件拒绝改为 Agent 的条件审批策略：

- 在 `tools/filesystem.py` 提供共用路径解析小函数，由工具和判定函数调用。使用 session workdir、`expanduser()`、`resolve()` 和 `is_relative_to()`，不能用字符串前缀比较；覆盖 `..`、绝对路径、符号链接及尚不存在的写入目标。
- `_file_path` 保留解析和普通文件检查，去掉“解析后越界就无条件抛错”的分支。文件 schema、父目录必须存在、UTF-8、唯一替换及输出限制保持不变；glob 继续保留自己的工作区边界。
- 三个文件工具的返回 `path`：区内用相对路径，区外用解析后的绝对路径。预先确定展示路径，不能保留写入/编辑之后无条件 `target.relative_to(workdir)` 的逻辑，否则副作用发生后仍会报错。
- 工具描述和 PathInput 的说明同步改为“相对工作区或绝对路径，工作区外访问由 Agent 审批”。审批约束属于生产 Agent 调用链；直接调用工具函数的可信 Python 代码不经过 HITL，不能再把工具单测当作权限集成验收。

无需增加可被模型伪造的授权字段、许可 token、上下文授权列表或独立审批账本。批准范围就是官方中断中那个 tool call。执行前后外部进程更换符号链接等竞态不作隔离保证；本阶段继续面向本地单用户 CLI。

### 3.4 同批工具与阶段边界

当前 HITL 在 `after_model` 中为同一 AI 响应中判定为 ask 的调用汇总一个中断。allow 和 deny 调用都不占 decisions 的位置；同名工具也可能因参数不同分别属于 allow/ask/deny。

只要同批存在 ask，整个工具节点尚未运行，allow 调用也会等待，deny 的错误消息在随后经过工具节点时产生。这里的 deny 优先表示“规则分类优先且绝不开放批准”，不要求在暂停前运行一段自建工具调度。恢复后由官方工具节点处理允许执行的操作，不强制串行、不承诺副作用顺序。只有 allow/deny 的批次不会因权限中断。

不提前实现 Todo、SubAgent、后台审批服务或嵌套子 Agent。应用数据结构必须能表示多个 interrupt ID；多 ID 的路由用框架探针验收，真实嵌套审批留在阶段六。开发阶段使用新 session，不迁移旧会话，也不承诺跨图结构升级恢复尚未结束的审批。

## 4. 框架接线与状态契约

### 4.1 Middleware 顺序及预算语义

建议列表顺序固定为：

```text
HumanInTheLoopMiddleware
ModelCallLimitMiddleware
ToolDenyMiddleware
ToolErrorMiddleware
ImageInputMiddleware
```

官方 `after_model` 按列表逆序执行。在上述顺序中，预算先记录已经发生的模型调用，随后 HITL 按条件暂停。ToolDenyMiddleware 只包装工具执行，不修改 after_model 状态；原有 wrap 行为仍分别处理工具错误和图片模型输入。

**该顺序已经预验证，不能简单把 HITL 追加到列表末尾。** 当 `run_limit=1` 时，追加到末尾会先中断，模型计数被推迟到 resume；恢复后还没发生新的模型调用，就可能在下一模型节点触发 `ModelCallLimitExceededError`。将 HITL 放在首位，恢复后的一次新模型调用可正常完成。

沿用官方 `run_limit`：限制一次 `ainvoke` 执行段，审批恢复的下一次 `ainvoke` 获得新的 run 预算。交互 ID 跨暂停保持一致，但预算不是跨所有审批恢复累计的交互总上限。README 需把原先“每次交互”的表述改准确；不新增跨恢复计数器，不操作官方私有计数字段，不以记录器累计预算。

保持 `ToolErrorMiddleware` 仅转换 `ToolException` 的行为。ToolDenyMiddleware 不捕获 handler 的异常；不得把 `GraphInterrupt` 或取消信号转成普通工具错误。正常顶层中断由图返回结果表达；异常边界仍应允许框架控制流传播，不把越过边界的控制流异常写成普通失败。对应探针继续保留。

### 4.2 采用已验证的默认返回协议

保留当前 `agent.ainvoke(...)` 默认接口，不在本阶段切换 `version="v2"`、streaming 或自建顶层图：

- 本次执行暂停：读取 `result.get("__interrupt__", ())`。
- 查询已有暂停：`snapshot = await agent.aget_state({"configurable": {"thread_id": session_id}})`，读取 `snapshot.interrupts`。
- 每个中断使用官方 `Interrupt.id` 与 `Interrupt.value`。`snapshot.next` 非空本身不能作为待审批依据，失败任务也可能留下下一节点。
- 仅在没有中断的正常返回中调用 `extract_answer`。中断结果的 `answer=null`、`error=null`，不写 `interaction_succeeded`。

本地锁定版本的 `ActionRequest` 参数字段是 **`args`**，不是官方页面部分示例中的 `arguments`。展示和解析按实际 `args` 实现，不为尚未使用的版本增加兼容分支。

建议 `InteractionResult` 调整：

| 字段 | 约定 |
| --- | --- |
| `status` | `Literal["succeeded", "failed", "interrupted"]` |
| `interrupts` | 默认空列表；每项包含 `id`、`action_requests`、`review_configs`，是当前官方中断的展示副本 |
| `interaction_id` | 已接受交互及恢复始终为原 ID；无法绑定有效交互的前置失败可为 `null`，不伪造恢复交互 |
| `answer` / `error` | 成功返回 answer；失败返回 error；待审批两者均为 null |
| `session_status` | 仍表示 `running/closed/unknown`；不把待审批写进 `session.json` |

单个中断的序列化形状如下，多个动作保留数组次序：

```json
{
  "id": "<interrupt-id>",
  "action_requests": [
    {"name": "write_file", "args": {"path": "../shared/note.txt", "content": "hello"}, "description": "Access outside workspace"}
  ],
  "review_configs": [
    {"action_name": "write_file", "allowed_decisions": ["approve", "reject"]}
  ]
}
```

有 `description` 时一并展示。小型结果/决策类型就近定义在 `application.py`；它们用于 I/O 校验，不发展为权限引擎。官方状态是唯一事实来源，序列化列表不另行持久化为审批状态。

### 4.3 新普通输入：先检查，再接受

调整 `ask` 的执行次序：

1. 保留本次消息校验，打开 session 并取得现有交互锁；锁内重新确认会话未关闭。
2. 打开 Checkpointer，使用原 workdir 构建 Agent，先以最小 thread config 查询当前 `snapshot.interrupts`。
3. 存在待审批时，返回 `status="failed"`、`error.type="session_pending_approval"`，附带当前 interrupts 和原交互 ID。此返回表示新请求未被接受，原交互继续暂停。
4. 没有待审批才创建本次交互 ID、记录 `user_input`，并提交 `{"messages": [message]}`。保持 callbacks、metadata 和 context 的现有接线。
5. 根据中断、成功或执行异常形成结果和对应记录，再释放资源与锁。

第 3 步不得写 `user_input` 或 `interaction_failed`，不得调用 `ainvoke`、更新图状态或覆盖原交互 metadata。此门禁同时覆盖 Python、单次 CLI 和交互 CLI；不能只在终端提示里限制输入。

等待用户思考期间不持有交互锁。锁只覆盖一次查询后的执行提交及结果收集，使其他进程可以查询或关闭会话；真正恢复前必须重新取得锁并校验最新中断。

### 4.4 查询与恢复入口

在 `application.py` 增加两个应用入口，沿用已有 `model` 参数供确定性测试注入：

```text
get_pending_approvals(config, session_id, *, model=None) -> ApprovalStatus
resume(config, session_id, decisions_by_interrupt, *, model=None) -> InteractionResult
```

`ApprovalStatus` 只含 `session_id`、`session_status`、待审批交互的 `interaction_id`（没有则为 null）和 `interrupts`。查询只读 `aget_state`，不调用模型或执行图，不记录一次新交互。关闭会话可以展示其保留的中断，但不能恢复。查询是展示快照，提交时不能据此跳过锁内复查。

恢复次序：

1. 打开原 session，取得 `interaction_lock()`，重读其生命周期；closed/busy/missing 沿用现有错误语义。
2. 重开相同 SQLite 并构建相同 Agent，查询最新中断。没有待审批返回 `no_pending_approval`。
3. 从该 snapshot 的 `metadata["interaction_id"]` 取得原交互 ID，并验证决策。缺失有效 ID 时返回 `invalid_checkpoint_metadata`，不从 trajectory 推断或生成替代 ID。
4. 全部校验通过后，用原 ID 创建 writer/recorder，记录决策提交，重新注入 session workdir 与现有 runtime 限制。
5. 使用相同 session/thread 执行 `agent.ainvoke(Command(resume=resume_map), ...)`，metadata 显式继续传原 `interaction_id`。不提交 HumanMessage，不拼接历史，不使用历史 checkpoint_id 分叉。
6. 与 ask 共用结果分类：可能成功、失败，也可能再次 interrupted。新的暂停继续沿用原交互 ID，并向用户返回当前中断。

`resume_map` 对单个和多个中断采用同一种形式：

```python
Command(resume={
    interrupt_id: {"decisions": [
        {"type": "approve"},
        {"type": "reject", "message": "请保留原文件"},
    ]},
})
```

外层键是 interrupt ID，内层 decisions 严格对应该中断的 `action_requests`。不能按工具名称构造决策字典；同名工具可以出现多次。也不能把所有中断的动作展平成一份无归属列表。

### 4.5 决策输入校验

提交给框架前，在同一锁内完成以下校验：

- 提供的 interrupt ID 集合与当前待审批集合完全一致。拒绝漏项、未知 ID、旧 ID 和空映射；首版一次提交当前全部中断，不实现部分提交。
- 每个中断的 decisions 长度等于 action_requests 长度，按下标逐项匹配 review_configs；不得重排、按名称去重或自动补批准。
- 仅允许 `approve` 和 `reject`，还需符合该项 `allowed_decisions`。拒绝 edit/respond、未知类型和额外决策字段；approve 不允许附带替换参数。
- reject 可带字符串 `message`；未填写时交给官方默认拒绝反馈。CLI 展示参数不能成为客户端回传并替换的执行参数。
- JSON 文件必须是预期对象形状；重复对象键、非法 JSON 和错误字段类型明确拒绝。

非法提交返回 `invalid_approval_decisions`，保留可再次查询的中断；不得先调用框架再依赖其异常完成校验。重复提交已经处理的决策应得到无待审或 ID 不匹配错误，不能再次执行工具。

一旦真实执行开始后发生异常，沿用执行失败结果并记录原交互的失败；不自动重试。调用方再次查询 Checkpoint 决定是否仍存在审批，不能依据 trajectory 缺少成功记录就重复提交副作用。任意崩溃窗口的 exactly-once 执行仍不在首版承诺内。

## 5. CLI 与本地记录

### 5.1 单次与非交互命令

新增两个命令，避免给现有 ask 增加一套含混的恢复参数：

```bash
# 危险操作请求：例如用 Bash 删除文件，返回 interrupted 和 session_id 后退出。
uv run rsh ask --config config/default.toml --workdir ./workdir --json "用 Bash 删除 cleanup.txt"

# 新进程查询当前待审动作，不推进 Agent。
uv run rsh approvals --config config/default.toml --session-id <SESSION_ID> --json

# decisions.json 的内容是上一节的 interrupt ID → decisions 对象。
uv run rsh resume --config config/default.toml --session-id <SESSION_ID> --decisions-file ./decisions.json --json
```

`decisions.json` 示例：

```json
{
  "<从 approvals 输出取得的 interrupt-id>": {
    "decisions": [{"type": "approve"}]
  }
}
```

- `ask` 和文件驱动的 `resume` 均不隐式弹出审批提示；需要问答式操作时使用现有根命令交互模式。
- 工作目录内创建/编辑 note.txt、普通 Bash 命令等直接返回执行结果；只有 ask 类操作返回 interrupted。deny 类操作作为错误 ToolMessage 反馈模型，不创建可批准项，也不必然导致整轮 failed。
- ask/resume 的执行退出码：成功 `0`，执行或前置校验失败 `1`，等待审批 `2`。再次暂停仍返回 `2`。Typer 自身的命令行语法错误按其原有行为处理。
- approvals 的查询成功退出码为 `0`，无待审时返回空 interrupts；查询失败为 `1`。是否可继续执行还要结合 session_status。
- `--json` 下 stdout 只包含一个完整 JSON 对象；诊断走 stderr，不插入 banner、审批问答或普通文本。执行状态以 JSON 的 status 为准。
- 非交互根命令遇到待审批时展示待审批结果和后续命令，退出 `2`；不得阻塞等确认，也不得把管道中的下一条普通输入当作批准。

### 5.2 交互模式

复用 `_interactive` 的单一异步事件循环和 PromptSession。打开已有 session 时，先查询待审批；每次 ask/resume 返回 interrupted 时进入同一审批流程。

1. 按 action_requests 顺序只展示工具名称和该工具将执行的操作（Bash 显示 command，其余工具显示紧凑参数）；不展示 session、workdir、中断 ID、风险描述或 review 配置。TTY 下普通 `rsh>` 提示为蓝色，审批输入提示为黄色。
2. 逐项输入 `y/yes` 或 `n/no`，分别映射为官方 `approve/reject`；空输入不能默认批准，交互输入不附加拒绝理由。
3. 收齐当前所有中断的全部决定后调用一次 resume；若再次暂停，展示新动作继续收集。
4. 收集期间的决定只存在内存。审批阶段只接受 `y/yes`、`n/no`；其他输入不会改变审批状态。Ctrl+C、Ctrl+D 丢弃未提交决定并保留框架暂停；已审一半也不能隐式提交部分批准。
5. 审批完成或取消后，普通交互阶段继续支持 `/status`、`/close`、`/quit`、`/exit`；待审批期间不解析这些命令，也不把它们作为普通问题接受。

读取审批的提示与选择走 stderr，最终回答走 stdout。不强制截断审批参数；如果以后引入分页，应保证确认前可以查看完整内容，不把缩略内容当作唯一批准依据。

### 5.3 轨迹事件

复用现有 writer 和 callback，应用层只需增加两类事件：

| 事件 | 时机与 payload |
| --- | --- |
| `interaction_interrupted` | 本次执行返回暂停；记录当前 interrupt ID、action_requests、review_configs |
| `approval_submitted` | 决策已通过锁内校验，准备提交 Command；记录 interrupt ID → decisions |
| 既有 `interaction_succeeded` / `interaction_failed` | 恢复的最终成功或实际执行失败，仍使用原交互 ID |

`approval_submitted` 只表示尝试提交，不能解释为副作用已经完成。只读查询、被拒的新普通输入和无效审批提交不写“原交互失败”事件。resume 不再记录 `user_input`。

每次调用产生新的框架 run/parent_run ID；同一逻辑交互跨恢复通过 `interaction_id` 关联，不强行复用旧 run ID。人工拒绝和硬拒绝都没有真实 tool_start/end，不伪造 callback 事件；人工拒绝原因在审批事件和框架工具消息中查看，硬拒绝原因保留在框架 error ToolMessage 中。未发生人工中断的普通操作不写 approval 事件。

删除、篡改或无法写入 trajectory 时，查询和恢复仍以 Checkpoint 为准。沿用 `recording_errors` 报告记录问题，不阻止已批准调用、不自动重试模型或工具。无需为此修改记录文件布局或把审批状态放进 `session.json`。

### 7.2 显式真实模型验收

在支持工具的现有 provider 上，使用隔离的临时 workdir/session，至少覆盖：

1. 工作目录内创建、读取、编辑文件并执行普通 cat 命令 → 不产生人工审批，原五工具链路直接完成。
2. 在临时 workdir 预先创建可删除文件，请求用 Bash 执行 `rm cleanup.txt` → 审批前文件存在；批准后删除。另一次独立交互拒绝相同类别操作 → 文件保留，模型收到拒绝反馈。
3. 在同一个测试临时根目录下创建两个同级目录，仅其中一个作为 session workdir；请求读写另一目录的预定文件 → 触发越界审批，批准可访问、拒绝不访问，返回路径正确。
4. 进程 A 触发危险操作审批并退出，B 查询后批准 → 同一 session/交互 ID；既有三轮文本、图片输入/恢复冒烟继续通过。

## 8. 依据与验证记录

### 8.1 官方依据与本地版本差异

通过 Context7 查询并核对官方页面，再读取已安装版本源码进行验证：

- [Human-in-the-loop](https://docs.langchain.com/oss/python/langchain/human-in-the-loop#conditional-interrupts)：when 条件审批、逐项决定、拒绝反馈及 after_model 中断。

- [Custom middleware](https://docs.langchain.com/oss/python/langchain/middleware/custom)：生命周期顺序与异步扩展。
- [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)：Checkpoint、StateSnapshot 和同 thread 状态恢复。

本地 `langchain/agents/middleware/human_in_the_loop.py` 的 `InterruptOnConfig`、`_should_interrupt` 确认 when 接收 ToolCallRequest，且其 ToolRuntime 带有可信 context、tool_call_id 和运行配置；条件为 False 的调用不进入待审列表。ActionRequest 使用 args 字段，description factory 与 when 的函数签名不同。StateSnapshot 具有 interrupts 字段。上述接口均可在现有锁定版本使用，无需升级依赖。
