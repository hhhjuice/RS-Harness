本阶段让现有 Agent 完成真实的模型—工具循环，并支持图片消息输入。完成标准是：五种生产工具经过默认工具执行机制运行，参数和路径错误可反馈给模型；Bash 有执行时限和输出限制；工具轨迹可查看；文本、文本加图片、仅图片均能提交；图片消息经过 SQLite 保存和重开后仍可用于后续对话。

## 2. 实施基线与范围

### 2.1 实施前接入点

### 2.2 范围与实施假设

- 工具运行在本地单用户环境，Bash 先验收 macOS/Linux 的 POSIX 进程行为，与现有会话锁的平台前提一致。
- 图片首版从 Python 消息入口及 `rsh ask --image` 提交。交互模式可继续同一图片会话；本阶段不增加附件暂存、拖拽或终端图片预览命令。
- 五工具在本阶段直接执行，在临时工作目录中测试。人工审批属于阶段四，不增加审批绕过开关。
- 延续每 session 同时只接收一次用户交互的规则；一次交互中的多个工具调用仍由框架处理，不增加全局锁、串行工具调度或同批拒绝逻辑。
- 保留既有模型预算和错误退出行为，不加入 Todo、SubAgent、MCP、后台任务、旧会话迁移或遥感专用工具。

## 3. 五种工具的契约

### 3.1 定义、注入与组装

新增 `tools/filesystem.py`、`tools/shell.py` 及必要的 `__init__.py`。四个文件工具可用同步小函数，由框架执行同步工具；Bash 使用异步子进程 API。全部通过 `@tool(args_schema=...)` 声明，业务参数用就近的 Pydantic 模型验证。

将已有 `AgentContext` 移到 `src/rs_harness/context.py`，由 `main.py`、`application.py` 和工具共同导入，避免“主 Agent 导入工具，工具反向导入主 Agent”的循环。它仅包含 `workdir`、`bash_timeout_s`、`max_tool_output_bytes`；工具通过 `ToolRuntime[AgentContext].context` 读取，不把可信工作目录或限制值暴露为模型可传参数。

`build_agent` 直接使用 `[read_file, write_file, edit_file, glob, bash]`。不建注册中心，不调整 `parallel_tool_calls` 或 `max_concurrency`，不设置自定义 `ToolNode`。提示词和工具描述说明：同批只提交独立操作；写入后读取、编辑后执行等依赖操作应分轮发起。数组顺序不代表副作用顺序，同一文件的并发修改不承诺事务性或确定结果。

参数 schema 明确类型、非空要求和数值范围。当前版本下，显式 `args_schema` 不应直接设置 `extra="forbid"`：框架注入的 `runtime` 会进入内部参数验证，可能被误拒绝。首版使用 Pydantic 默认额外字段处理，严格验证已声明的业务字段，并测试模型不能通过传入 `runtime/workdir` 覆盖可信 context；不为此开发通用 schema 适配层。

### 3.2 工具参数与结果

工具成功返回可 JSON 序列化的字典，由框架形成 `ToolMessage`。不手工创建成功消息或管理 `tool_call_id`。预期的执行失败抛出官方 `ToolException`，由第 4 节转换；错误不能伪装成空文件或空匹配结果。

| 工具 | 模型可见参数 | 行为与结果 |
| --- | --- | --- |
| `read_file` | `path: str`；`offset: int = 1`；`limit: int = 200` | 按 1 起始行号读取 UTF-8 普通文件；offset/limit 为严格正整数，limit 最大 2000；返回 `path/content/start_line/end_line/truncated`。空文件或超出末行返回空内容，末行可为 null |
| `write_file` | `path: str`；`content: str` | 创建文件或覆盖现有普通文件，允许空内容；父目录必须存在，不隐式创建目录；返回 `path/bytes_written` |
| `edit_file` | `path: str`；`old_text: str`；`new_text: str` | UTF-8 精确替换；old_text 非空且必须恰好匹配一次，new_text 可为空；零次或多次匹配均报错且不写文件；返回 `path/replacements`，成功时 replacements 为 1 |
| `glob` | `pattern: str` | workdir 下按模式匹配普通文件，支持 `**`；返回排序后的相对路径 `paths` 和 `truncated`，最多 200 项；无匹配是成功的空列表 |
| `bash` | `command: str` | 在 session workdir 中运行非空 Bash 命令，返回 `exit_code/stdout/stderr/timed_out/truncated`；超时或非零退出通过错误消息携带同样的执行信息 |

路径与命令字符串只用去空白结果判断是否为空，不擅自改写原始文件名、命令或写入内容。文件读取和编辑保留原换行，不自动规范化 CRLF。编辑先完成全部匹配校验，再执行写入；不增加模糊匹配、批量补丁或自动重试。

`read_file` 同时受行数和输出字节限制，保留原始内容，行号用字段表示。若字节限制截在行中，标记 `truncated=true`，不声称返回了完整末行；解码时不产生半个 UTF-8 字符。`glob` 的 200 项是本阶段返回数量约定，并受输出字节预算约束；它包含点文件，不读取 `.gitignore`，不实现内容搜索。

### 3.3 文件路径边界

四个文件工具共用 `filesystem.py` 内的小型路径解析函数；复用达到实际需要后再拆文件。

1. 相对路径以 `runtime.context.workdir` 为基准；允许绝对路径，但规范化后仍必须位于 workdir 内。用路径关系判断，不能用字符串前缀判断。
2. 对 `..`、符号链接、尚不存在的写入目标及其已有父目录进行解析后检查。逃逸到工作目录外的显式路径返回 `ToolException`；目录、设备、FIFO 等不是文件读写目标。
3. `glob` 拒绝绝对模式和包含 `..` 路径段的模式；不递归跟随目录符号链接。对匹配项再做解析和边界检查，越界项不返回；显式文件工具访问同一路径仍报错。
4. 相对路径始终来自 session，不受当前进程后续切换 cwd 影响；两个 session 使用各自工作目录。

这些检查是文件工具的逻辑边界，不是操作系统沙箱。Bash 的 `cwd` 只决定起始目录，命令仍可访问当前用户有权限访问的其他路径；不使用危险命令子串清单冒充隔离。并发外部进程更换符号链接等竞态也不在本阶段隔离承诺内。

### 3.4 Bash 生命周期与资源限制

新增以下 `[runtime]` 配置，并加入 `Config.summary()`、示例和参数校验：

| 字段 | 默认值 | 作用 |
| --- | --- | --- |
| `bash_timeout_s` | `60` | 单次命令从启动到输出收集结束的时限；有限正数，拒绝布尔值 |
| `max_tool_output_bytes` | `65536` | 单次工具返回的正文预算，严格正整数；Bash 的 stdout 与 stderr 共用预算 |

默认值是 RSH 的资源选择，不是框架默认值。`max_tokens` 继续只控制模型输出，不作为命令输出限制。写入工具只返回摘要，不回显整个输入内容；输入文件可读取量与输出预算的差异要在实现中保留，不能先无界缓存命令输出再截断。

Bash 使用 `asyncio.create_subprocess_exec` 启动 `/bin/bash -c command`，设置 workdir、独立进程组、`stdin=DEVNULL` 和两个输出管道。持续并行消费 stdout/stderr，达到总字节预算后继续排空但丢弃后续内容，设置截断标志；不承诺两条流之间的全局顺序。

超时后先终止进程组，在固定短宽限期后强制结束仍存活的进程，并回收进程和管道任务。清理不能只杀 shell 主进程，也不能因 shell 已退出但子进程持有管道而永久等待。保留已收集的受限输出，反馈超时、退出信息和截断状态。

收到异步取消时执行同样的清理，再重新抛出取消信号；不能把取消包装成普通工具失败。超时测试覆盖普通子进程及持有管道的后代；主动脱离进程组的守护进程不属于本阶段保证，工具不提供后台任务语义。

## 4. 工具错误与运行记录

### 4.1 复用官方异步错误包装

在 `build_middleware` 中按顺序返回：

1. 现有 `ModelCallLimitMiddleware`。
2. 官方 `ToolErrorMiddleware(on_error=...)`，仅将 `ToolException` 转为可读错误文本，其他异常返回 `None` 继续传播。

当前锁定版本的 `ToolErrorMiddleware` 已实现异步工具包装，满足总方案的 `wrap_tool_call` 错误处理要求，无需再复制一份自定义 `awrap_tool_call`。不引入工具重试 middleware。

文件工具只将预期的路径、编码和 OS 文件操作错误转成 `ToolException`；Bash 将启动失败、超时、非零退出转成含执行事实的 `ToolException`。未知程序错误继续成为现有 `InteractionResult(status="failed")` 和 `interaction_failed`，不以大范围 `except Exception` 把程序缺陷变成模型可反复尝试的错误。

| 情况 | 框架行为与应用约定 |
| --- | --- |
| 参数不符合 Pydantic schema | 默认工具节点返回 `ToolMessage(status="error")`，不另做参数调度或重复转换 |
| 预期工具执行失败 | 官方错误 middleware 返回 error ToolMessage，保留原 `tool_call_id`，模型可修正后再调用 |
| 非预期工具异常 | 传播到应用失败路径；不重新执行有副作用的工具 |
| `GraphInterrupt` 等框架中断 | 原样传播；只用最小探针验“不被吞掉”，本阶段不实现审批交互 |
| 异步取消 | Bash 完成资源清理后传播；不转换成工具错误文本 |

一次工具失败后模型仍可给出正常回答，整轮结果可以是 succeeded；工具失败和交互失败不是同一概念。预算仍限制后续模型调用，不能撤销已完成的写入或命令。

### 4.2 记录器扩展

使用已有 `TrajectoryRecorder` 和 `TrajectoryWriter`，按本地官方 callback 签名增加：

| callback | 事件 | payload |
| --- | --- | --- |
| `on_tool_start` | `tool_start` | 工具名、公开输入参数、可用时的 tool_call_id |
| `on_tool_end` | `tool_end` | 官方返回结果，包括可用的消息状态和 tool_call_id |
| `on_tool_error` | `tool_error` | 异常类型和消息 |

统一保留已有 session_id、interaction_id、run_id、parent_run_id。以 callback 的 run 关系关联事件，不按日志相邻顺序配对，也不把 run_id 当成 tool_call_id。开始事件优先使用结构化 `inputs`，缺失时保存官方 input_str；不尝试从字符串反推参数。

本地已验证：`ToolException` 会产生 start→error，随后中间件转换成模型可见错误，不再产生 end；参数验证错误也可产生 start→error。取消可能只有 start，不能把“每个 start 必须有 end”设为验收条件。模型响应中的工具请求与框架结果可用于开发排查，不另建一份工具执行账本。

`user_input` 保存本次提交内容的观测摘要：文本块和 URL 图片块原样保留，本地图片的 base64 不进入记录副本，替换为 MIME、字节数和 SHA-256 摘要（对解码后原始字节计算）。不在每轮导出完整历史；模型起始事件继续只记摘要。记录失败沿用 `recording_errors`，不能触发模型/工具重试，也不改变 Checkpoint。并发调用下每行 JSON 必须完整可解析。

## 5. 多模态输入与 CLI

### 5.1 标准消息和本次输入职责

扩展 `build_human_message(text="", *, images=(), workdir=...)`。images 是按用户顺序排列的本地路径或 HTTP(S) URL；返回单个 `HumanMessage`。纯文本沿用 `HumanMessage(content=text)`，有图片时构造官方内容块：

```python
HumanMessage(content_blocks=[
    {"type": "text", "text": "描述图片中的内容"},
    {"type": "image", "url": "https://example.com/sample.png"},
    {"type": "image", "base64": encoded_image, "mime_type": "image/png"},
])
```

上例仅说明字段；实际内容由入口读取生成。仅图片输入省略文本块，不拼接虚构问题；没有非空文本且没有图片时才属于 empty_input。多图顺序与 `--image` 参数顺序一致。

- 本地相对图片路径以目标 session 的 workdir 解析，新 session 使用本次选定 workdir。用户明确提供的绝对图片路径可以在 workdir 外：这是用户附件入口，文件工具的自动访问边界仍按第 3.3 节执行。
- 只读取本次显式附件；本地普通文件在入口读取一次（受 harness 级 32 MiB 读取上限保护）、编码为 base64，并附带匹配的 MIME。拒绝缺失、目录、空文件和无法识别为图像的输入；不只凭 URL 后缀判断远程 MIME。
- URL 仅接受具有主机名的 HTTP(S) 地址，直接形成 URL block，由 provider 读取；不主动下载、不做 URL 缓存或本地路径回退。`file://`、直接传入的 data URI 和其他协议不作为 CLI 输入形式。
- 格式、单图大小、图像数量及请求总大小以实际 model/provider 的官方限制为准。实现第一个关口须记录所选 provider 的能力和限制，能在本地确定的限制在编码/调用前检查；URL 内容及完整解码合法性由 provider 校验，失败明确返回，不自动丢弃图片重试。
- `model.profile` 的 `image_inputs` 可作为已知模型的能力依据；缺失不能解释为支持或不支持。自定义 `base_url` 也不能仅凭同名模型套用 OpenAI 能力。未知组合通过显式真实模型测试确认，失败如实返回；不建设全 provider 能力注册表。

不沿用旧版 32 MiB、固定遥感格式清单或 `image_ref` 协议，不增加 `read_image`。本阶段不做自动缩放、转码、裁剪、音视频输入或图片生成。若所选模型的格式/大小限制尚未核实，应把对应项标为待验，不能用框架接受内容块代替模型能力验收。

### 5.2 应用接线与持久化

`ask` 的第三参数扩展为 `str | HumanMessage`：字符串仍经过现有构造函数，HumanMessage 直接作为本次消息提交。CLI 在进入 `ask` 前构造好图片消息，避免重复读取和 base64 编码；Python 调用方也可先调用 `build_human_message`。入口拒绝空消息，不接受一组“完整历史消息”作为此次输入。

每轮仍然只调用 `ainvoke({"messages": [message]}, ...)`。context、callbacks、metadata、session 锁及 thread_id 的接线保持现有职责，不从 trajectory 或图片源路径重建历史。

SQLite 保存完整标准块。后续本地原图被删除或改写时，Checkpoint 中的 base64 保持原值；使用同 session、新进程、纯文本追问，仍应向模型提供原图像块。URL 消息只保存 URL，不保证远程资源永久可达或内容不变；恢复验收应分别核对“标准块被保存”与“provider 此时能获取 URL”。

纯文本回答继续使用现有 `extract_answer` 和 `InteractionResult`。不因输入图片新增输出文件协议或把图像数据塞入 session 元数据。只有实际输入验证通过才调用模型；输入错误不会追加一条不完整的用户消息到 Checkpoint。

### 5.3 最小 CLI 入口

把 `ask` 文本位置参数改为可选，增加可重复的 `--image`：

```bash
uv run rsh ask --config config/default.toml --image ./sample.png "描述这张图片"
uv run rsh ask --config config/default.toml --image ./sample.png --json
uv run rsh ask --config config/default.toml --image ./first.png --image https://example.com/second.png "比较两张图"
uv run rsh ask --config config/default.toml --session-id <SESSION_ID> "继续说明上一张图片"
```

执行顺序为：加载配置 → 确定已有 session 或新会话的 workdir → 构造并验证本次消息 → 必要时创建 session → 调用 `ask`。已有 session 的 workdir 不能被新 `--workdir` 改绑；进程 cwd 变化不影响附件相对路径。

没有文本也没有图片时沿用空输入不创建 session 的行为。无效本地附件在新会话创建前失败；已有会话不写入无效消息。输入阶段的失败统一为清楚的错误及退出码 1；`--json` 的非空错误输出也必须是合法 JSON，创建前没有 session_id 时使用独立错误对象，不伪造会话 ID。成功和执行阶段失败继续使用 `InteractionResult`，诊断提示写 stderr。

交互模式仍共用一个异步事件循环，可通过 `--session-id` 续聊图片消息；保留中文编辑、空行、退出和关闭会话行为。

## 6. 实施顺序与文件范围

### 9.2 Provider 验证与输入限制

实际使用 `deepseek-flash`，服务为 `https://api.deepseek.com`。通过 Context7 和 [DeepSeek 官方 Vision 文档](https://api-docs.deepseek.com/guides/vision) 核对当前服务契约：

- JPEG、PNG、GIF、WebP；根据内容识别格式。
- 内联/URL 单图上限 32 MiB；完整请求体上限 48 MiB；每请求最多 600 张图片。
- 不使用 file_id 时图片总计不超过 64 MiB；URL 不超过 8192 字符，远端下载时限为 60 秒。
- 单边尺寸上限 8192 像素；请求包含 15 张或以上图片时为 4096 像素。

本地图片读取统一受 32 MiB 上限保护：这是 harness 级内存防护（读取本身有界），恰与该服务单图上限一致，对所有 provider 生效。其余数量/请求体/URL 长度检查仅对该官方 endpoint 和已核实模型使用；其他服务不自动套用。

入口读取本身有界（一次最多读 32 MiB + 1 字节并按实际读取字节数判定超限），并在编码时检查 base64 预算。增加 `ImageInputMiddleware`，在每次模型调用前检查包含 Checkpoint 历史的图数、已知内联字节数和 base64 请求下界，避免只检查当前一轮。middleware 不拼装或修改消息历史。完整请求 JSON 开销、远程图片字节数、图像解码和像素尺寸仍由 provider 最终校验；本地文件头识别不声称能完整解码图片。超限或不支持会报错，不自动删图、缩放、转码或改成纯文本重试。

已知官方模型 profile 明确不支持图片时可在模型包装入口报错；自定义 base_url 不仅凭同名 OpenAI profile 判断能力。Python 输入构造函数可传入 config 提前启用已知限制；application 和模型调用路径仍校验实际消息。
